# Architecture

The whole game is a pure function plus a word list. Keeping it that way is the
design goal.

---

## 1. Stack

| Choice | What | Why |
| --- | --- | --- |
| **No backend** | Static site | The answer pool is fixed and public. A server would only add cost and latency |
| **TypeScript** | Strict mode | The tile-marking and normalisation rules are exactly the kind of thing types catch |
| **Vite** | Build + dev server | Fast, boring, good static output |
| **Vanilla DOM or Preact** | View layer | The UI is a grid, a keyboard and a card. A framework is optional here — pick one and stop thinking about it |
| **Vitest** | Tests | Same config as the build |
| **localStorage** | Persistence | No accounts in v1 |

Hard constraint: **the scoring logic imports nothing.** No framework, no DOM, no
storage. It is a pure function over two strings, so it is trivially testable and
cannot be broken by a UI refactor.

## 2. Layout

```
src/
  core/                  ← pure, zero dependencies, 100% covered by tests
    score.ts             ← the two-pass tile algorithm (game-design.md § 3)
    keyboard-state.ts    ← max-merge of letter states across guesses
    normalise.ts         ← the single place that touches case and umlaut aliases
    attempts.ts          ← ceil(length / 2) + 3
    select.ts            ← daily + practice answer selection
    game.ts              ← the state machine; reducer over (state, action)
    types.ts             ← shared vocabulary; no behaviour
  data/
    words.<n>.json       ← generated by build:words, never hand-edited
    guesses.txt.gz       ← extended guess list
  ui/
    dom.ts    ← el()/announce() helper, the only DOM abstraction
    setup.ts  grid.ts  keyboard.ts  definition-card.ts  stats.ts
  store/
    persist.ts           ← localStorage read/write + schema migration
  main.ts                ← wiring: actions, render, physical keyboard
scripts/
  import_goethe.py       ← PDF → candidates + review queue (Python: pypdf)
  build-words.ts         ← validate → src/data/words.<n>.json (+ pool table)
data/
  words/<n>.json         ← the curated source of truth, reviewed by humans
  words.sample.json      ← thirteen reference entries
```

`core/` must not import from `ui/`, `store/` or `data/`. Enforce it with an ESLint
`no-restricted-imports` rule rather than good intentions.

## 3. Game state machine

```
        choose(length)          submit(valid)         won / lost
 setup ───────────────▶ playing ─────────────▶ playing ──────────▶ reveal
   ▲                      │                                          │
   │                      │ submit(invalid) → rejected, no attempt    │
   └──────────────────────┴──────────────────────────────────────────┘
                            playAgain()
```

```ts
type GameState = {
  status: 'setup' | 'playing' | 'won' | 'lost';
  length: 3|4|5|6|7|8;
  answerId: string;          // id, not the word — see § 6
  guesses: { letters: string[]; marks: Mark[] }[];
  current: string[];         // the row being typed
  maxAttempts: number;       // from attempts.ts
};
```

Implemented as a reducer over actions — `CHOOSE_LENGTH`, `TYPE_LETTER`,
`BACKSPACE`, `SUBMIT`, `REVEAL`, `PLAY_AGAIN`. Reasons: an invalid guess must
reject without mutating anything; the state must serialise to localStorage as-is so a
refresh mid-round resumes; and the whole thing stays testable without a DOM.

**Only `SUBMIT` scores.** Nothing about tile colour is computed while typing —
otherwise a half-typed row can leak information through a render path.

## 4. Normalisation: one place only

Four transformations exist, and mixing them up is the likeliest source of a
correctness bug in this codebase. `core/normalise.ts` owns all four and nothing else
may do any of them:

| Function | Does | Used by |
| --- | --- | --- |
| `toComparable(s)` | `toLowerCase()` + NFC assert | Scoring, guess validation |
| `umlautFor(ch)` | dead key + `a/o/u/s` → `ä/ö/ü/ß` | Physical-keyboard input only |
| `toTile(ch)` | `toUpperCase()`, but `ß → ß` | Grid rendering only |
| `letters(s)` | `[...s]` — never `s[i]` | Everywhere a word is indexed |

Rules that follow, and each deserves a test:

- **Never strip diacritics.** No `normalize('NFD').replace(/\p{Diacritic}/gu, '')`
  anywhere. `Käse` and a hypothetical `Kase` are different words; the umlaut is the
  lesson.
- **Never fold `ß` to `ss` in comparison.** `ß` is one letter and one tile.
  `Straße` is 6 tiles, not 7.
- **Umlaut entry is input-side only.** It runs when a keystroke enters the current
  row, never when a guess is scored. The scorer only ever sees real letters.
  Digraph collapsing was specified here originally and removed after measurement —
  `ss` appears in 26 pool words and `ue` in 9, so `tasse` would have become `taße`.
  A dead key (`;`/`"`) cannot collide with a letter.
- **`toTile('ß')` returns `'ß'`,** not `'SS'` (which would break the tile count) and
  not `'ẞ'` U+1E9E (which many fonts lack).

## 5. Daily word selection

Six daily puzzles exist — one per length — and every player must get the same word
for a given (date, length).

```ts
// Deterministic, no network, no stored server state.
function dailyAnswer(pool: Word[], isoDate: string, length: number): Word {
  const period = pool.length;                       // e.g. 34 at length 3
  const epoch  = daysSince('2026-01-01', isoDate);  // fixed launch epoch
  const cycle  = Math.floor(epoch / period);
  // A per-cycle shuffle: within one cycle every word appears exactly once.
  const order  = seededShuffle(pool, hash(`${length}:${cycle}`));
  return order[epoch % period];
}
```

Why a shuffled permutation rather than `pool[hash(date) % pool.length]`: independent
sampling would repeat words within days — unacceptable at length 3, where the pool is
34. A permutation guarantees a player sees all 34 before any repeat, and reshuffles
each cycle so the order is not memorisable.

Fix the epoch date in a constant and never change it, or every historical puzzle
shifts.

**Practice mode** draws uniformly from the pool, excluding the last *N* answers seen
(N ≈ 20, or `pool.length / 3` for short pools) so it does not feel repetitive.

## 6. On hiding the answer

It cannot be hidden. This is a static client-side game: the word list ships to the
browser and a determined player can read it from the network tab or the source map.
Accept it and design accordingly:

- Keep the **answer id** in the game state, not the plaintext word, so the answer
  isn't sitting in a `window`-reachable object or in a React DevTools tree.
- Ship the bundle **obfuscated only as a speed bump** (e.g. base64 with a fixed XOR),
  clearly commented as *not security*. It stops idle DOM-poking, nothing more.
- **Never** ship the daily answers in a separate easy-to-read `daily.json`.
- Do not add server-side answer checking to "fix" this. The threat model is a learner
  spoiling their own puzzle, which is their business.

## 7. Persistence

```jsonc
// localStorage key "dw:v1"
{
  "schema": 1,
  "settings": { "validation": "dictionary", "hints": false, "colourBlind": false, "theme": "system" },
  "inProgress": { "5": { "answerId": "a2-tasse", "guesses": ["essen", "kaufe"], "date": "2026-09-11" } },
  "stats": {
    "5": { "played": 12, "won": 10, "streak": 3, "bestStreak": 6, "distribution": [0,1,3,4,2,0,0], "wordsSeen": ["a2-tasse"] }
  }
}
```

- **Versioned under `schema`,** with migrations in `store/persist.ts`. Data loss
  because of an unversioned shape change is a self-inflicted wound.
- **Stats are keyed by length** — see [game-design.md § 10](game-design.md#10-stats).
- **`inProgress` is keyed by length too**, so a player can have an unfinished 5- and
  8-letter round at once, and each carries its `date` so a stale daily round is
  discarded at midnight rather than resumed.
- `wordsSeen` stores ids and is the number that reflects actual learning. It grows
  unboundedly but at 878 possible ids that is a few KB — fine.
- Every read is wrapped in `try/catch` and falls back to defaults. Private-mode
  browsers throw on access, and the game must still be playable.

## 8. Testing

The scoring function is where bugs hide, so it gets table-driven tests. Non-negotiable
cases:

| Answer | Guess | Expected | Guards against |
| --- | --- | --- | --- |
| `tasse` | `essen` | 🟨🟨🟩⬜⬜ | The repeated-letter bug (game-design.md § 3) |
| `tasse` | `tasse` | 🟩🟩🟩🟩🟩 | Win detection |
| `kaffee` | `kaffee` | all green | Two separate doubled letters |
| `kaffee` | `feiern` | 🟨🟨⬜🟨⬜⬜ | Doubles in the answer, singles in the guess — both `e`s of the answer are still available, so both `e`s of the guess go yellow |
| `straße` | `straße` | 6 tiles, all green | `ß` is one letter, not `ss` |
| `käse` | `kase` | `ä` vs `a` mismatch | No diacritic stripping |
| `zug` | `zug` | 3 tiles | Minimum length |
| `arbeiten` | `arbeiten` | 8 tiles | Maximum length |

Plus: `attemptsFor` matching the table (5,5,6,6,7,7); keyboard state never downgrades
green→yellow; `dailyAnswer` is stable for a fixed (date, length) and covers the whole
pool over one cycle; every curated lemma passes guess validation in every tier that
should accept it.

## 9. The Android app

`mobile/` is a React Native app on Expo SDK 57. It exists because "run it on a phone"
was a real requirement; the web app is unchanged and still the reference
implementation.

**What made this cheap** is the rule from § 1 that `core/` imports nothing. The port
reused `src/core` and `src/data` as-is and added no game logic. What had to be
rewritten was the view layer, the styles and the storage adapter.

**The store was split** to make that possible without duplicating rules:

| File | Role |
| --- | --- |
| `src/store/stats.ts` | The persisted shape, `hydrate`/`migrate`, and the stats rules. No I/O |
| `src/store/persist.ts` | Web adapter: `localStorage` in, `localStorage` out |
| `mobile/storage.ts` | Mobile adapter: `AsyncStorage`, the same `hydrate` and rules, async |

So a schema change cannot be handled one way on web and another on mobile.

**Three platform decisions** that have no web equivalent, each documented at the
point of use in `mobile/`:

1. **Metro cannot resolve `core`'s `.js` extensions.** `src/core` is Node-style ESM,
   where `'./types.js'` means `types.ts`. Vite, vitest and tsx remap that; Metro
   fails. `mobile/metro.config.js` adds a `resolveRequest` hook that strips the
   extension.
2. **Android safe areas.** RN's own `SafeAreaView` does nothing on Android, and
   SDK 54+ is edge-to-edge by default, so `react-native-safe-area-context` supplies
   the insets. Without it the header sits under the status bar.
3. **`String.prototype.normalize` is guarded** in `core/normalise.ts`, because Hermes
   has historically shipped without it. Safe because `build-words.ts` already fails
   the build on any lemma that is not NFC.

The APK is built with `npm run apk` in `mobile/` (prebuild + `gradlew
assembleRelease`) or on EAS. See [mobile/README.md](../mobile/README.md) — including
what has been verified and what has not.
